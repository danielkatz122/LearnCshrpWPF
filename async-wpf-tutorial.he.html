תכנות אסינכרוני ב-C# ו-WPF

מדריך מפורט: מהיסודות של async/await, דרך בניית ממשקי WPF, ועד לשילוב ביניהם – עם דוגמאות קוד מלאות ותרגילים עם פתרונות.

הקדמה

אפליקציות שולחניות מודרניות צריכות להישאר מגיבות גם כשהן מבצעות עבודה ארוכה: הורדת קבצים, קריאה ממסד נתונים, חישובים כבדים ועוד. משתמש שלוחץ על כפתור ורואה חלון "לא מגיב" (Not Responding) – יחווה את האפליקציה כתקולה.

המדריך בנוי מארבעה חלקים:

  1. חלק א׳ – תכנות אסינכרוני ב-C#: Task, async, await, ביטול, דיווח התקדמות וטיפול בשגיאות.
  2. חלק ב׳ – יסודות WPF: XAML, פקדים, Data Binding, MVVM וה-UI Thread.
  3. חלק ג׳ – שילוב השניים: דוגמאות מלאות ומעשיות.
  4. חלק ד׳ – תרגילים מדורגים עם רמזים ופתרונות מלאים.
דרישות מקדימות היכרות בסיסית עם C# (מחלקות, מתודות, lambda), ו-.NET 8 SDK מותקן. ליצירת פרויקט WPF חדש: 
dotnet new wpf -n AsyncWpfDemo
cd AsyncWpfDemo
dotnet run

חלק א׳ – תכנות אסינכרוני ב-C#

1. למה אסינכרוני?

בקוד סינכרוני כל שורה מחכה שהקודמת תסתיים. אם שורה אחת מחכה לרשת במשך 3 שניות – ה-Thread שמריץ אותה חסום ולא עושה שום דבר אחר. בקוד אסינכרוני אנחנו אומרים: "התחל את הפעולה, ובזמן שמחכים – שחרר את ה-Thread לעבודה אחרת. כשהתוצאה תגיע – המשך מכאן".

חשוב להבחין בין שני סוגי עבודה:

סוגדוגמאותהפתרון המתאים
I/O-bound (תלוי קלט/פלט) קריאת קובץ, בקשת HTTP, שאילתת מסד נתונים await על מתודה אסינכרונית אמיתית (ReadAsync, GetStringAsync...) – לא צריך Thread נוסף בזמן ההמתנה.
CPU-bound (תלוי מעבד) חישוב מספרים ראשוניים, עיבוד תמונה, דחיסה await Task.Run(...) – העבודה רצה על Thread מה-ThreadPool כדי לא לחסום את ה-Thread הנוכחי.
אנלוגיה מלצר (Thread) שלוקח הזמנה למטבח לא עומד ליד הטבח עד שהמנה מוכנה (חסימה). הוא ממשיך לשרת שולחנות אחרים, וכשהמנה מוכנה – הוא (או מלצר אחר) מגיש אותה. זו בדיוק המשמעות של await.

2. Task ו-async/await

Task מייצג פעולה שמתבצעת (או תתבצע) ברקע. Task<T> מייצג פעולה שבסופה תחזיר ערך מסוג T. המילה async מסמנת מתודה שמותר להשתמש בתוכה ב-await, ו-await אומר "חכה לסיום ה-Task בלי לחסום את ה-Thread".

Program.cs – אפליקציית Console
using System.Diagnostics;

var sw = Stopwatch.StartNew();

string a = await DownloadFakeAsync("A", 2000);
string b = await DownloadFakeAsync("B", 1000);
Console.WriteLine($"{a}, {b} – {sw.ElapsedMilliseconds} ms");   // ~3000 ms

sw.Restart();
Task<string> taskA = DownloadFakeAsync("A", 2000);   // מתחילים את שתיהן יחד
Task<string> taskB = DownloadFakeAsync("B", 1000);
Console.WriteLine($"{await taskA}, {await taskB} – {sw.ElapsedMilliseconds} ms");   // ~2000 ms

static async Task<string> DownloadFakeAsync(string name, int delayMs)
{
    Console.WriteLine($"מתחיל {name}");
    await Task.Delay(delayMs);   // מדמה המתנה לרשת
    Console.WriteLine($"סיים {name}");
    return $"תוצאה-{name}";
}

שימו לב: קריאה למתודה אסינכרונית מתחילה את הפעולה מיד ומחזירה Task. ה-await הוא הנקודה שבה מחכים לתוצאה. לכן אם מתחילים כמה פעולות לפני שעושים await – הן רצות במקביל.

מוסכמת שמות מתודות אסינכרוניות מסתיימות ב-Async: LoadDataAsync, SaveAsync. זה עוזר לזכור שצריך לעשות להן await.

3. מה קורה מאחורי הקלעים

הקומפיילר הופך כל מתודת async למכונת מצבים (State Machine). כל await הוא נקודת "פיצול":

  1. הקוד רץ באופן סינכרוני עד ה-await הראשון.
  2. אם ה-Task שממתינים לו כבר הסתיים – ממשיכים מיד (בלי לשחרר את ה-Thread).
  3. אחרת – המתודה חוזרת לקורא שלה עם Task שעדיין לא הושלם, וה-Thread חופשי.
  4. כשה-Task מסתיים, שאר המתודה (ה-continuation) מתוזמן לריצה. אם היה SynchronizationContext (כמו ב-WPF) – ההמשך ירוץ באותו Thread שממנו התחלנו.
UI Thread: [click] -> [code before await] -> (free! handles other events...) -> [code after await] | ^ Network: +------------- waiting for response -------------+

הנקודה הרביעית היא המפתח לשילוב עם WPF – נחזור אליה בחלק ג׳.

4. טיפוסי החזרה

טיפוסמתי משתמשים
Taskמתודה אסינכרונית שלא מחזירה ערך (המקבילה של void).
Task<T>מתודה אסינכרונית שמחזירה ערך מסוג T.
ValueTask<T>אופטימיזציה כשלעתים קרובות התוצאה זמינה מיד (למשל מ-Cache). לשימוש מתקדם בלבד.
async voidרק ל-Event Handlers (כמו Button_Click). אי אפשר לעשות לה await, וחריגה שנזרקת ממנה עלולה להפיל את האפליקציה.
// ✔ נכון

public async Task<int> CountAsync() { ... }
private async void SaveButton_Click(object sender, RoutedEventArgs e) { await SaveAsync(); }

// ✘ לא נכון – אי אפשר לחכות לה ולתפוס ממנה חריגות
public async void SaveData() { ... }

5. Task.Run, Task.WhenAll, Task.WhenAny

Task.Run – העברת עבודת CPU ל-ThreadPool

int result = await Task.Run(() =>
{
    int sum = 0;
    for (int i = 0; i < 500_000_000; i++) sum += i % 7;
    return sum;
});
אל תעטפו I/O ב-Task.Run await Task.Run(() => File.ReadAllText(path)) עובד, אבל מבזבז Thread שיושב וחוסם. עדיף: await File.ReadAllTextAsync(path).

Task.WhenAll – המתנה לכמה פעולות במקביל

Task<string> t1 = http.GetStringAsync("https://example.com");
Task<string> t2 = http.GetStringAsync("https://example.org");
Task<string> t3 = http.GetStringAsync("https://example.net");

string[] pages = await Task.WhenAll(t1, t2, t3);   // הזמן הכולל ≈ האיטית מביניהן

Task.WhenAny – הראשונה שמסתיימת

Task<string> download = http.GetStringAsync(url);
Task timeout = Task.Delay(TimeSpan.FromSeconds(5));

Task first = await Task.WhenAny(download, timeout);
if (first == timeout)
    Console.WriteLine("הפעולה לקחה יותר מדי זמן");
else
    Console.WriteLine(await download);
קיצור ב-.NET 6 ומעלה await download.WaitAsync(TimeSpan.FromSeconds(5)); זורק TimeoutException אם עבר הזמן.

6. טיפול בחריגות

חריגה שנזרקת בתוך מתודה אסינכרונית "נשמרת" בתוך ה-Task, ונזרקת מחדש בנקודת ה-await. לכן try/catch רגיל עובד בדיוק כמצופה: 

try
{
    string html = await http.GetStringAsync("https://does-not-exist.invalid");
}
catch (HttpRequestException ex)
{
    Console.WriteLine($"שגיאת רשת: {ex.Message}");
}

עם Task.WhenAll, ה-await זורק רק את החריגה הראשונה. כדי לראות את כולן – בודקים את Exception של ה-Task: 

Task all = Task.WhenAll(tasks);
try
{
    await all;
}
catch
{
    foreach (Exception inner in all.Exception!.InnerExceptions)
        Console.WriteLine(inner.Message);
}

7. ביטול – CancellationToken

ביטול ב-.NET הוא שיתופי: מי שרוצה לבטל יוצר CancellationTokenSource וקורא ל-Cancel(); מי שעושה את העבודה מקבל CancellationToken ובודק אותו. 

using var cts = new CancellationTokenSource();
cts.CancelAfter(TimeSpan.FromSeconds(3));   // ביטול אוטומטי אחרי 3 שניות

try
{
    await CountSlowlyAsync(cts.Token);
}
catch (OperationCanceledException)
{
    Console.WriteLine("בוטל!");
}

static async Task CountSlowlyAsync(CancellationToken token)
{
    for (int i = 1; i <= 10; i++)
    {
        token.ThrowIfCancellationRequested();   // בדיקה ידנית (חשוב בלולאות CPU)
        Console.WriteLine(i);
        await Task.Delay(1000, token);          // מתודות של .NET מקבלות token ישירות
    }
}

8. דיווח התקדמות – IProgress<T>

הממשק IProgress<T> מאפשר לפעולה אסינכרונית לדווח על התקדמות. המימוש המובנה Progress<T> לוכד את ה-SynchronizationContext ברגע שהוא נוצר, ולכן אם יוצרים אותו ב-UI Thread – ה-callback ירוץ ב-UI Thread. מושלם לעדכון ProgressBar! 

var progress = new Progress<int>(percent => Console.WriteLine($"{percent}%"));
await ProcessItemsAsync(progress);

static async Task ProcessItemsAsync(IProgress<int> progress)
{
    for (int i = 1; i <= 100; i++)
    {
        await Task.Delay(30);
        progress.Report(i);
    }
}

9. ConfigureAwait(false)

כברירת מחדל, await חוזר ל-SynchronizationContext המקורי (ב-WPF: ה-UI Thread). ConfigureAwait(false) אומר "לא משנה לי באיזה Thread אמשיך".

  • בקוד ספרייה (שירותים, גישה לנתונים) שלא נוגע ב-UI – מומלץ ConfigureAwait(false). זה חוסך מעברים מיותרים ל-UI Thread.
  • בקוד UI (Event Handlers, ViewModels) – אל תשתמשו בו, כי אחרי ה-await תרצו לגעת בפקדים.
// בתוך ספריית שירותים
public async Task<string> LoadConfigAsync(string path)
{
    string text = await File.ReadAllTextAsync(path).ConfigureAwait(false);
    return text.Trim();   // לא נוגעים ב-UI – אז לא משנה באיזה Thread אנחנו
}

10. מלכודות נפוצות

  • .Result / .Wait() – חוסמים את ה-Thread. ב-UI Thread זה עלול לגרום ל-Deadlock (ראו תרגיל 8). הכלל: async all the way.
  • Fire-and-forget – קריאה למתודה אסינכרונית בלי await: חריגות "נבלעות" ואין דרך לדעת מתי הפעולה הסתיימה.
  • async void מחוץ ל-Event Handlers.
  • Thread.Sleep בקוד אסינכרוני – חוסם. השתמשו ב-await Task.Delay.
  • שכחת await – הקומפיילר מזהיר (CS4014). אל תתעלמו מהאזהרה!

חלק ב׳ – WPF

1. מה זה WPF?

Windows Presentation Foundation היא טכנולוגיה של מיקרוסופט לבניית אפליקציות שולחניות ל-Windows. עקרונותיה המרכזיים:

  • הפרדה בין עיצוב ללוגיקה – הממשק מוגדר ב-XAML (שפת סימון מבוססת XML), והלוגיקה ב-C#.
  • גרפיקה וקטורית מואצת חומרה – הממשק מתרחב יפה לכל רזולוציה.
  • Data Binding עוצמתי – חיבור אוטומטי בין נתונים לממשק.
  • Styles ו-Templates – שליטה מלאה במראה של כל פקד.

4. Data Binding

במקום לכתוב GreetingText.Text = ... ידנית, אפשר לקשור מאפיין של פקד למאפיין של אובייקט נתונים (ה-DataContext). כדי שהממשק יתעדכן כשהערך משתנה – המחלקה צריכה לממש INotifyPropertyChanged.

ViewModelBase.cs
using System.ComponentModel;
using System.Runtime.CompilerServices;

public abstract class ViewModelBase : INotifyPropertyChanged
{
    public event PropertyChangedEventHandler? PropertyChanged;

    protected void OnPropertyChanged([CallerMemberName] string? name = null) =>
        PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(name));

    protected bool SetField<T>(ref T field, T value, [CallerMemberName] string? name = null)
    {
        if (EqualityComparer<T>.Default.Equals(field, value)) return false;
        field = value;
        OnPropertyChanged(name);
        return true;
    }
}
PersonViewModel.cs
public class PersonViewModel : ViewModelBase
{
    private string _name = "";

    public string Name
    {
        get => _name;
        set
        {
            if (SetField(ref _name, value))
                OnPropertyChanged(nameof(Greeting));
        }
    }

    public string Greeting => string.IsNullOrWhiteSpace(Name) ? "" : $"שלום, {Name}!";
}
<StackPanel Margin="20">
    <TextBox Text="{Binding Name, UpdateSourceTrigger=PropertyChanged}" />
    <TextBlock Text="{Binding Greeting}" FontSize="16" Margin="0,10,0,0" />
</StackPanel>
public MainWindow()
{
    InitializeComponent();
    DataContext = new PersonViewModel();
}

לרשימות משתמשים ב-ObservableCollection<T> – היא מודיעה לממשק על הוספה והסרה של פריטים.

5. MVVM ו-ICommand

MVVM (Model-View-ViewModel) הוא דפוס הארכיטקטורה המקובל ב-WPF:

  • Model – הנתונים והלוגיקה העסקית (שירותים, גישה לנתונים).
  • View – ה-XAML. כמעט בלי קוד ב-Code-Behind.
  • ViewModel – מחזיק את מצב המסך ומחשף מאפיינים ו-פקודות שה-View נקשר אליהם.

במקום אירוע Click, כפתור נקשר ל-ICommand:

RelayCommand.cs
using System.Windows.Input;

public class RelayCommand : ICommand
{
    private readonly Action _execute;
    private readonly Func<bool>? _canExecute;

    public RelayCommand(Action execute, Func<bool>? canExecute = null)
    {
        _execute = execute;
        _canExecute = canExecute;
    }

    public event EventHandler? CanExecuteChanged
    {
        add => CommandManager.RequerySuggested += value;
        remove => CommandManager.RequerySuggested -= value;
    }

    public bool CanExecute(object? parameter) => _canExecute?.Invoke() ?? true;
    public void Execute(object? parameter) => _execute();
}
<Button Content="נקה" Command="{Binding ClearCommand}" />

כשה-CanExecute מחזיר false – הכפתור מושבת אוטומטית.

6. ה-UI Thread וה-Dispatcher

זה הנושא הכי חשוב להבנת השילוב עם async:

  • לכל אפליקציית WPF יש UI Thread אחד שמריץ לולאת הודעות (Message Loop): מצייר את המסך, מטפל בלחיצות עכבר, מקלדת וכו׳.
  • פקדי WPF הם בעלי Thread Affinity: מותר לגשת אליהם רק מה-Thread שיצר אותם. ניסיון לגשת מ-Thread אחר יזרוק InvalidOperationException: "The calling thread cannot access this object because a different thread owns it."
  • אם ה-UI Thread עסוק בעבודה ארוכה – אף אירוע לא מטופל והחלון "קופא".
  • ה-Dispatcher הוא התור של ה-UI Thread. דרכו אפשר לבקש מה-UI Thread להריץ קוד: Dispatcher.InvokeAsync(...).
המסקנה צריך (1) לא לחסום את ה-UI Thread, ו-(2) לגשת לפקדים רק מה-UI Thread. async/await פותר את שתי הבעיות בבת אחת!

using System.IO;
using System.Net.Http;
using System.Windows;

namespace AsyncWpfDemo;

public partial class MainWindow : Window
{
    private static readonly HttpClient Http = new();
    private CancellationTokenSource? _cts;

    public MainWindow() => InitializeComponent();

    private async void DownloadButton_Click(object sender, RoutedEventArgs e)
    {
        _cts = new CancellationTokenSource();
        DownloadButton.IsEnabled = false;
        CancelButton.IsEnabled = true;
        DownloadProgress.Value = 0;

        // נוצר ב-UI Thread, לכן ה-callback ירוץ ב-UI Thread
        var progress = new Progress<int>(percent =>
        {
            DownloadProgress.Value = percent;
            StatusText.Text = $"{percent}%";
        });

        try
        {
            byte[] data = await DownloadWithProgressAsync(UrlBox.Text, progress, _cts.Token);
            StatusText.Text = $"הורדו {data.Length:N0} בתים";
        }
        catch (OperationCanceledException)
        {
            StatusText.Text = "ההורדה בוטלה";
        }
        catch (Exception ex) when (ex is HttpRequestException or InvalidOperationException or UriFormatException)
        {
            StatusText.Text = $"שגיאה: {ex.Message}";
        }
        finally
        {
            DownloadButton.IsEnabled = true;
            CancelButton.IsEnabled = false;
            _cts.Dispose();
            _cts = null;
        }
    }

    private void CancelButton_Click(object sender, RoutedEventArgs e) => _cts?.Cancel();

    private static async Task<byte[]> DownloadWithProgressAsync(
        string url, IProgress<int> progress, CancellationToken token)
    {
        using HttpResponseMessage response =
            await Http.GetAsync(url, HttpCompletionOption.ResponseHeadersRead, token);
        response.EnsureSuccessStatusCode();

        long? total = response.Content.Headers.ContentLength;
        await using Stream stream = await response.Content.ReadAsStreamAsync(token);
        using var buffer = new MemoryStream();

        byte[] chunk = new byte[81920];
        long readSoFar = 0;
        int read;
        while ((read = await stream.ReadAsync(chunk, token)) > 0)
        {
            buffer.Write(chunk, 0, read);
            readSoFar += read;
            if (total > 0)
                progress.Report((int)(readSoFar * 100 / total.Value));
        }
        return buffer.ToArray();
    }
}

  • finally מבטיח שהממשק יחזור למצב תקין בכל מקרה.

private static int CountPrimes(int limit)
{
    int count = 0;
    for (int n = 2; n <= limit; n++)
        if (IsPrime(n)) count++;
    return count;
}

private static bool IsPrime(int n)
{
    if (n < 2) return false;
    for (int i = 2; (long)i * i <= n; i++)
        if (n % i == 0) return false;
    return true;
}

4. MVVM עם AsyncRelayCommand

ב-MVVM אין Event Handlers, ולכן צריך פקודה שיודעת להריץ מתודה אסינכרונית ולהשבית את עצמה בזמן הריצה.

AsyncRelayCommand.cs
using System.Windows.Input;

public class AsyncRelayCommand : ICommand
{
    private readonly Func<Task> _execute;
    private readonly Func<bool>? _canExecute;
    private bool _isRunning;

    public AsyncRelayCommand(Func<Task> execute, Func<bool>? canExecute = null)
    {
        _execute = execute;
        _canExecute = canExecute;
    }

    public event EventHandler? CanExecuteChanged
    {
        add => CommandManager.RequerySuggested += value;
        remove => CommandManager.RequerySuggested -= value;
    }

    public bool CanExecute(object? parameter) => !_isRunning && (_canExecute?.Invoke() ?? true);

    // async void מותר כאן: ICommand.Execute הוא למעשה Event Handler
    public async void Execute(object? parameter)
    {
        _isRunning = true;
        CommandManager.InvalidateRequerySuggested();
        try
        {
            await _execute();
        }
        finally
        {
            _isRunning = false;
            CommandManager.InvalidateRequerySuggested();
        }
    }
}

6. SynchronizationContext ו-Dispatcher.InvokeAsync

WPF מתקינה DispatcherSynchronizationContext על ה-UI Thread. כש-await מתחיל ב-UI Thread הוא שומר את ההקשר הזה, ובסיום ממשיך דרכו – זה כל ה"קסם".

מתי בכל זאת צריך Dispatcher ידנית? כשקוד רץ על Thread אחר ולא הגיע לשם דרך await מה-UI. דוגמאות:

  • אירועים שמגיעים מ-Thread רקע: FileSystemWatcher, System.Timers.Timer, SerialPort, חיבורי Socket.
  • עדכון ביניים מתוך לולאה ארוכה בתוך Task.Run (אם כי IProgress<T> עדיף).
private FileSystemWatcher? _watcher;

private void StartWatching(string folder)
{
    _watcher = new FileSystemWatcher(folder) { EnableRaisingEvents = true };
    _watcher.Created += async (s, e) =>
    {
        // האירוע מגיע מ-Thread של ה-ThreadPool
        await Dispatcher.InvokeAsync(() => FilesList.Items.Add(e.Name));
    };
}
לטיימרים ב-UI עדיף DispatcherTimer – ה-Tick שלו רץ ב-UI Thread. או לולאה פשוטה עם await Task.Delay (ראו תרגיל 1), או PeriodicTimer מ-.NET 6.

public record FileStats(long Lines, long Words, long Chars);

private async void PickButton_Click(object sender, RoutedEventArgs e)
{
    var dialog = new OpenFileDialog { Filter = "Text files|*.txt;*.csv;*.log|All files|*.*" };

    PickButton.IsEnabled = false;
    StatsText.Text = "קורא...";
    var progress = new Progress<int>(p => ReadProgress.Value = p);
    try
    {
        FileStats stats = await AnalyzeFileAsync(dialog.FileName, progress);
        StatsText.Text = $"שורות: {stats.Lines:N0} | מילים: {stats.Words:N0} | תווים: {stats.Chars:N0}";

    catch (IOException ex)

        StatsText.Text = $"שגיאה: {ex.Message}";
    }
    finally
    {
        PickButton.IsEnabled = true;
    }
}

private static async Task<FileStats> AnalyzeFileAsync(string path, IProgress<int> progress)
{
    long lines = 0, words = 0, chars = 0;
    int lastPercent = -1;

    using var reader = new StreamReader(path);
    long length = Math.Max(1, reader.BaseStream.Length);
    string? line;
    while ((line = await reader.ReadLineAsync().ConfigureAwait(false)) != null)
    {
        lines++;
        chars += line.Length;
        words += line.Split((char[]?)null, StringSplitOptions.RemoveEmptyEntries).Length;

        int percent = (int)(reader.BaseStream.Position * 100 / length);
        if (percent != lastPercent)
        {
            lastPercent = percent;
            progress.Report(percent);
        }
    }
    progress.Report(100);
    return new FileStats(lines, words, chars);
}

Progress<int> נוצר ב-UI Thread, ולכן גם עם ConfigureAwait(false) בתוך המתודה – העדכון של ה-ProgressBar יגיע ל-UI Thread.

private static List<int> FindPrimes(int limit, IProgress<int> progress, CancellationToken token)
{
    var primes = new List<int>();
    int lastPercent = -1;
    for (int n = 2; n <= limit; n++)
    {
        if (n % 10_000 == 0)
        {
            token.ThrowIfCancellationRequested();
            int percent = (int)((long)n * 100 / limit);
            if (percent != lastPercent)
            {
                lastPercent = percent;
                progress.Report(percent);
            }
        }
        if (IsPrime(n)) primes.Add(n);
    }
    progress.Report(100);
    return primes;
}

private static bool IsPrime(int n)
{
    if (n < 2) return false;
    if (n % 2 == 0) return n == 2;
    for (int i = 3; (long)i * i <= n; i += 2)
        if (n % i == 0) return false;
    return true;
}

תרגיל 5 – חיפוש תוך כדי הקלדה (Debounce) בינוני

מטרה: ביטול פעולה קודמת כשמתחילה חדשה – תבנית נפוצה מאוד בממשקים.

דרישות:

  • צרו רשימה של 500,000 מחרוזות אקראיות בטעינת החלון.
  • בכל הקלדה ב-TextBox – חפשו את המחרוזות שמכילות את הטקסט והציגו עד 200 תוצאות.
  • החיפוש מתחיל רק אחרי 300ms בלי הקלדה (Debounce).
  • אם המשתמש מקליד שוב בזמן חיפוש – החיפוש הקודם מבוטל ותוצאותיו לא מוצגות.

תרגיל 6 – AsyncRelayCommand עם פרמטר וביטול מתקדם

מטרה: לבנות תשתית MVVM אסינכרונית שימושית.

דרישות:

  • מחלקה AsyncCommand<T> שמקבלת Func<T?, CancellationToken, Task>.
  • מאפיין IsRunning עם INotifyPropertyChanged (כדי לקשור אליו ב-XAML).
  • מאפיין CancelCommand (מסוג ICommand) שמבטל את הריצה הנוכחית, ופעיל רק בזמן ריצה.
  • חריגות (פרט לביטול) נשמרות במאפיין LastError במקום להפיל את האפליקציה.
  • השתמשו בה ב-ViewModel שמדמה "שליחת דוח" לפי שם שנבחר ב-ComboBox (הפרמטר).
רמז הורישו מ-ViewModelBase ומממשו ICommand. במקום CommandManager.RequerySuggested, הפעילו את CanExecuteChanged ידנית כשה-IsRunning משתנה. את CancelCommand אפשר לממש עם ה-RelayCommand מחלק ב׳.

using System.Windows.Input;

public class AsyncCommand<T> : ViewModelBase, ICommand
{
    private readonly Func<T?, CancellationToken, Task> _execute;
    private readonly Func<T?, bool>? _canExecute;
    private CancellationTokenSource? _cts;
    private bool _isRunning;
    private string? _lastError;

    public AsyncCommand(Func<T?, CancellationToken, Task> execute, Func<T?, bool>? canExecute = null)
    {
        _execute = execute;
        _canExecute = canExecute;
        CancelCommand = new RelayCommand(() => _cts?.Cancel(), () => IsRunning);
    }

    public ICommand CancelCommand { get; }

    public bool IsRunning
    {
        get => _isRunning;
        private set
        {
            if (SetField(ref _isRunning, value))
            {
                CanExecuteChanged?.Invoke(this, EventArgs.Empty);
                CommandManager.InvalidateRequerySuggested();   // מרענן את CancelCommand
            }
        }
    }

    public string? LastError
    {
        get => _lastError;
        private set => SetField(ref _lastError, value);
    }

    public event EventHandler? CanExecuteChanged;

    public bool CanExecute(object? parameter) =>
        !IsRunning && (_canExecute?.Invoke(Cast(parameter)) ?? true);

    public async void Execute(object? parameter) => await ExecuteAsync(Cast(parameter));

    public async Task ExecuteAsync(T? parameter)
    {
        _cts = new CancellationTokenSource();
        LastError = null;
        IsRunning = true;
        try
        {
            await _execute(parameter, _cts.Token);
        }
        catch (OperationCanceledException)
        {
            LastError = "הפעולה בוטלה";
        }
        catch (Exception ex)
        {
            LastError = ex.Message;
        }
        finally
        {
            IsRunning = false;
            _cts.Dispose();
            _cts = null;
        }
    }

    private static T? Cast(object? parameter) => parameter is T t ? t : default;
}

{

תרגיל 8 – אבחון ותיקון Deadlock מתקדם

מטרה: להבין לעומק את הקשר בין SynchronizationContext, .Result ו-ConfigureAwait.

העתיקו את הקוד הבא לפרויקט והריצו. לחצו על הכפתור – האפליקציה תקפא לתמיד.

private void LoadButton_Click(object sender, RoutedEventArgs e)
{
    string data = GetDataAsync().Result;
    ResultText.Text = data;
}

private async Task<string> GetDataAsync()
{
    await Task.Delay(1000);
    return "הנתונים הגיעו";
}

משימות:

  1. הסבירו במילים שלכם, שלב אחר שלב, למה נוצר Deadlock.
  2. תקנו בשלוש דרכים שונות, וציינו מה היתרונות והחסרונות של כל דרך.
  3. הסבירו למה אותו קוד בדיוק לא נתקע באפליקציית Console.
רמז מי ממתין למי? ה-UI Thread ממתין ל-Task. ה-Task, כדי להסתיים, צריך להריץ את השורה return ... – על איזה Thread?
פתרון

1. למה נוצר Deadlock

  1. LoadButton_Click רץ ב-UI Thread וקורא ל-GetDataAsync().
  2. GetDataAsync מגיע ל-await Task.Delay, לוכד את ה-SynchronizationContext של ה-UI ומחזיר Task לא גמור.
  3. .Result חוסם את ה-UI Thread עד שה-Task יסתיים.
  4. אחרי שנייה ה-Delay מסתיים. ההמשך (return "...") צריך לרוץ ב-UI Thread – הוא נשלח לתור של ה-Dispatcher.
  5. אבל ה-UI Thread חסום ב-.Result ולא מעבד את התור. ההמשך לא ירוץ לעולם, ה-Task לא יסתיים לעולם, ו-.Result לא ישתחרר לעולם.

2. שלוש דרכי תיקון

א. async all the way (הפתרון הנכון):

private async void LoadButton_Click(object sender, RoutedEventArgs e)
{
    string data = await GetDataAsync();
    ResultText.Text = data;
}

✔ לא חוסם בכלל, הממשק מגיב. ✘ אין חסרונות של ממש – זו הדרך המומלצת.

ב. ConfigureAwait(false) בתוך המתודה:

private async Task<string> GetDataAsync()
{
    await Task.Delay(1000).ConfigureAwait(false);
    return "הנתונים הגיעו";
}

✔ ההמשך רץ ב-ThreadPool ולכן ה-Task מסתיים ו-.Result משתחרר. ✘ ה-UI עדיין קופא לשנייה. ✘ שביר: אם מתודה פנימית כלשהי בשרשרת שוכחת ConfigureAwait(false) – ה-Deadlock חוזר.

ג. הרצה ב-Task.Run ואז המתנה:

string data = Task.Run(() => GetDataAsync()).Result;

✔ בתוך Task.Run אין SynchronizationContext, ולכן ההמשכים רצים ב-ThreadPool. ✘ ה-UI עדיין קופא. ✘ מבזבז Thread. ✘ חריגות עטופות ב-AggregateException. להשתמש רק כשאין ברירה (למשל בתוך constructor או מימוש של ממשק סינכרוני שאי אפשר לשנות).

3. למה Console לא נתקע

באפליקציית Console אין SynchronizationContext (הוא null). לכן ההמשך אחרי await רץ על Thread כלשהו מה-ThreadPool, לא צריך את ה-Thread החסום, ה-Task מסתיים ו-.Result משתחרר. זו בדיוק הסיבה שקוד "שעבד בבדיקות" נתקע כשמעבירים אותו ל-WPF.

סיכום ודף עזר

עקרונות מרכזיים

  1. אל תחסמו את ה-UI Thread – לא Thread.Sleep, לא .Result, לא .Wait(), ולא חישובים ארוכים ישירות.
  2. I/O → await על API אסינכרוני. CPU → await Task.Run(...).
  3. גישה לפקדים רק מה-UI Thread – אחרי await חוזרים אליו אוטומטית.
  4. async void רק ל-Event Handlers, ותמיד עם try/catch.
  5. ביטול עם CancellationToken, התקדמות עם IProgress<T>.
  6. מנעו הפעלה כפולה – השביתו כפתורים או השתמשו ב-CanExecute.
  7. ConfigureAwait(false) – בספריות ושירותים, לא בקוד UI.
